## 1. Problem

The Terminal must be the daily working surface for agentic development on two projects (Evonome, Modula Stack), and today it cannot run one job end-to-end. The E0 #355 live dogfood validated the Lead plumbing but could not reach a Lead ↔ Coder ↔ Verifier round-trip because the launch path fails open, dead sessions accumulate with no recovery, shared stores poison themselves, and every board/approval read still targets the **retired GitHub world** (archived repos + Projects v2 + a shared 5k/hr GraphQL pool observed exhausted at 5000/5000). Concretely, on the live instance today:

- **12 of 12 persisted jobs are dead** (`groups.json`: all `status:"exited"`, 55 panes `recoverability:"stale"`, `statusReason:"tmux_session_missing"`) with no archive or relaunch path — a perpetually red board.
- **18 of 44 conversation records are invalid** (legacy `review-session:*` / `review-history:*` records), and one bad record makes `loadConversations` throw for the whole file — page-bot surfaces down.
- The **context-brief spawn gate cannot be passed from any UI surface and cannot be observed when driven by API** — the #1 functional blocker (§2, F-1..F-4).
- The **project registry still binds both projects to `hyperbotsx/*` GitHub repos and Projects v2 URLs** (frozen archives since the 2026-07-27 forge cutover), so launch approval reads frozen state and metadata repair burns a dead rate pool.

## 3. Goals

1. **Launch works and is observable**: an approved FRD launches from the board through the Context-Brief gate to a live trio+Lead, with every spawn and gate transition logged and verified — or failing loudly with a reason and a retry.
2. **Sessions have a full lifecycle**: liveness is checked continuously; a dead job is recoverable or cleanly archivable; a backend restart reattaches; the board is never perpetually red.
3. **Forgejo is the only forge**: board, launch approval, issue links, metadata repair, review triggers, and closeout all read/write `forge.modulastack.com` through the forge adapter; zero GitHub calls remain in these paths.
4. **Two projects, first-class**: Evonome and Modula Stack are both configured, switchable from the shell in one action, and every scoped surface (board, launches, WIP slots, page bots, memory, state) respects the selection.
5. **No manual pokes**: stalled panes are re-driven and renewal-parked agents are resumed by the server, using the wiring that already exists.
6. **Dogfoodable headlessly**: launch → spawn → message → teardown is exercisable via API without a browser, in CI and against a live instance.

## 4. Non-goals

- **E1 Teams / roster launch**, PL3+ planning lanes, R2 board reskin — own FRDs per `page-briefs/00-index.md`.
- **The full MW-26/MW-27 activity ledger + continuation supervisor** (`frd-agent-activity-ledger-draft.md`) — this FRD ships only the bounded stall→re-drive and renewal→resume wiring in §7 CP-6; harness-emitted turn events stay in the ledger FRD.
- **Z4 runner split execution** — but every session-layer change lands behind the supervisor seam so Z4's extraction (F-11) is a move, not a rewrite.
- **needs_lead transport verdict** (E0-FF) — unchanged.
- **Executing the Evonome repo migration to the forge** (`evonome-repo-migration-deferred` runbook) — this FRD makes the Terminal multi-project-ready and repoints the registry; migrating the SoldierOne history to `ModulaStack/evonome` stays the existing ops runbook, a kickoff prerequisite for the Evonome half of AC-10.
- **Coms transport internals** (R1–R5: durable queues, reply-loss, single outbound slot, TTL env-wiring) — confirmed defects with line numbers are recorded in F-28 for the comms-contract FRD to consume; this FRD reads coms state but does not change the transport.
- No tenancy, auth, or user model changes.

## 5. Design rulings

### 5R.1 — Session management: **harden the in-house layer (option a); herdr is rejected as a control-plane dependency.** 

The two failure classes separate cleanly (addendum requirement): the #1 blocker is **orchestration** — the app never verifies what it spawned (F-3..F-6) — and no session manager fixes a call that is never checked. Session management proper (F-7..F-9) is where a robust layer earns its keep, and the audit shows the in-house layer is **not fundamentally inadequate**: creation, attach, scrollback replay, persistence, restart reconciliation, and kill all exist and work (F-9, F-10). What is missing is bounded: a periodic liveness check (~10 lines around the existing `hasTmuxSession`), spawn verification, logging, and recovery actions. That fails the KISS bar for a new dependency ("standard libraries before exotic dependencies"; herdr 0.4.8 is installed but is another daemon, a second session namespace, and its own failure domain — and the web app would still need all of its attach/WS/replay plumbing plus an adapter).

The decisive argument is architectural (F-11): Z4 FR-4 extracts **this exact layer** into the local runner, "driven by the same wire messages the localhost UI uses today." Hardening the in-house layer *is* the runner-prep work; adopting herdr now would couple the control plane to a subsystem on the wrong side of an unbuilt seam, then require un-coupling it again at Z4. Ruling:

- Consolidate session operations behind one **`SessionSupervisor` seam** (create/verify/attach/capture/inject/kill/liveness — today's `tmuxSupervisor` + `paneInjection` call surface, one interface, no behavior change). The seam is the Z4 extraction boundary; a runner daemon (herdr or otherwise) may implement it **runner-side, later, behind Z4's wire contract** — never as a control-plane peer.
- Concurrency/scale (two projects, many sessions) stays on the existing per-project `executionSlotCount` + lane caps (F-24), enforced at launch admission — not delegated to a session manager.

### 5R.2 — Board source: **Forgejo issues + `status:*` labels via REST; keep the existing board pages and regeneration flow.**

Per operator decision D-1, workflow state already lives in `status:*` labels + the app's own surfaces; Projects v2 is retired. The KISS move is to re-source `generate.py`'s fetch layer (F-18) from the Forgejo REST API (`AGENTOPS_FORGE_FORGEJO_URL`/token, self-hosted, no shared rate pool) — issues + labels + state map onto the same `board-data.js` shape — rather than rebuild the board UI (that is R2, gated on PL2/PL3 behavior per the index). Lanes/columns derive from `status:*` and `type:prd` labels; the Projects-v2 "field" concepts (F-20) retire with closeout moving to label writes. This removes A2's root cause outright; the remaining GraphQL backoff work is reduced to deleting the callsites.

### 5R.3 — Launch approval and forge ops go through the **existing Python forge adapter**; no TS forge client is written.

F-29 changes the shape of this work: the adapter, the Forgejo backend, and boards-as-labels all exist — the migration is **routing, not building**. The TS server reaches the forge the same way it already reaches closeout/sync/teardown: the delegate-to-`agentops-harness`-CLI pattern (thin new CLI verbs where needed), with `AGENTOPS_FORGE_BACKEND=forgejo` + the status-label map flipping the already-routed CLIs by configuration. Specifics:
- `canonicalPrdApproved` (F-19) becomes an adapter issue read (same contract: open + `type:prd` + `status:approved` + `/ceo approved:\s*yes/i` — the checks are already host-neutral).
- `generate.py` swaps `gh project item-list`/`gh issue` for adapter reads of issues + `status:*` labels; launch metadata (working branch / worktree / base) reads from the **issue body**, which `launchMetadataFix.ts:200-204` already writes — the `gh project` field reads retire with Projects v2.
- Metadata repair (A2) becomes advisory label reconciliation: launch proceeds with a warning when repair fails; it never hard-blocks on a cosmetic call.
- The Kody trigger follows the proven Forgejo-native shape (F-30): webhook `/forgejo/webhook`, `@modula start-review` comment via adapter `review.request` (fallback `@kody`), findings read via Forgejo comments (replacing the `gh api` reads in `kodyReview.ts:119-125`, `kodyReviewSync.ts:50-51`).
- PR create/read/merge (`preparePr.ts:42,260,272`, `mergeMain.ts:53,63`) route through adapter `pulls.*`; `completionGithubEnv.ts` gains the forge-host credential equivalent (its `insteadOf` wiring hardcodes github.com :39-52).

### 5R.4 — Context-Brief gate: close the loop end-to-end, one path.

The gate's routing/artifact/continue logic is sound and already mirrored by the manual Phase-0 workflow; what is missing is (i) an input surface, (ii) an actually-verified spawn, (iii) one path. Ruling: launch surfaces collect `scope`/`surfaces`/`policy` (defaulting from per-project action config); **lane launches route through the same `contextBriefLaunch` gate** (closing F-2); the brief group spawns under CP-1 verification; `continue` stays as built. The trio wrappers' Phase-0/Phase-1 manual gate retires once AC-1 passes (dogfood the in-app brief on this very FRD — `dogfood-context-brief-phase0` decision).

### 5R.5 — Store poisoning: quarantine, never fail-whole-file.

`loadConversations` skips-and-quarantines invalid records (moved to `conversations.quarantine.json`, logged once), with a one-time startup migration for the 18 legacy records (F-13). Same policy for any shared JSON store that currently throws on partial invalidity. `projectId` becomes boundary-validated: one `resolveProjectId` helper at the HTTP boundary that accepts only registry slugs, 400s with the offending value and expected shape (F-14), and the frontend only ever sends ids obtained from the registry API.

## 7. Functional requirements & checkpoints

Each CP: coder implements + tests → verifier reviews → Lead disposition; Git Manager commits per CP. Sequenced so a real FRD can be run from the board at the earliest possible CP.

**CP-1 — Spawn truth (A1 core).** FR-1: every spawn attempt/outcome logged with reason; FR-2: post-spawn verification (grace-period tmux check + coms-registration deadline for agent panes) with failure ⇒ group `error` + `statusReason` + partial-kill + UI surface + retry endpoint (respawn, not inject); FR-3: `reusableGroup` verifies liveness; FR-4: brief-state transitions (`pending`→`ready`/`degraded`/`failed`) logged and surfaced. *Tests:* wrapper-dies-instantly ⇒ error-with-reason (not silent running); reuse of a killed group respawns.
